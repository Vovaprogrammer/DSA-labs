## 2. Реализации и аналитическая оценка сложности

### 2.1 Сумма элементов массива — `array_sum`

```python
def array_sum(a: list[int]) -> int:
    total = 0
    for num in a:
        total += num
    return total
```

**O(n).** Один проход по массиву, на каждом элементе одна операция сложения.
Ветвлений нет, поэтому лучший, средний и худший случай — это одно и то же.

### 2.2 Поиск максимума — `array_max`

```python
def array_max(a: list[int]) -> int:
    max_val = a[0]
    for i in range(1, len(a)):
        if a[i] > max_val:
            max_val = a[i]
    return max_val
```

**O(n).** Тоже один проход. Число сравнений всегда n-1 независимо от
данных, а вот число обновлений `max_val` зависит от порядка элементов —
но на порядок роста это не влияет.

### 2.3 Подсчёт пар равных элементов — `count_equal_pairs`

```python
def count_equal_pairs(a: list[int]) -> int:
    count = 0
    n = len(a)
    for i in range(n):
        for j in range(i + 1, n):
            if a[i] == a[j]:
                count += 1
    return count
```

**O(n²).** Двойной цикл перебирает все пары (i, j), i < j — таких пар
n(n-1)/2. Причём это не просто худший случай, а Θ(n²): цикл всегда
проходит по всем парам, независимо от того, сколько из них реально равны.

### 2.4 Бинарное возведение в степень — `binary_pow`

```python
def binary_pow(x: int, n: int, mod: int | None = None) -> int:
    result = 1
    if mod is not None:
        x %= mod
    while n > 0:
        if n % 2 == 1:
            result = (result * x) % mod if mod is not None else result * x
        x = (x ** 2) % mod if mod is not None else x ** 2
        n //= 2
    return result
```

**O(log n).** Идея: разложить n по битам и переиспользовать уже посчитанные
квадраты `x, x², x⁴, x⁸, ...` вместо n умножений подряд. На каждой итерации
`n` делится на 2, поэтому число итераций равно числу бит в n, то есть
⌊log₂ n⌋ + 1.

**Зачем модуль.** Без `mod` числа `x` при каждом возведении в квадрат растут
экспоненциально по количеству цифр (в Python это не переполнится, но
считаться будет всё дольше). Тогда умножение перестаёт быть операцией за
константное время, и замер покажет не число итераций цикла, а то, как
Python умножает длинные числа. С фиксированным `mod` все промежуточные
значения ограничены по размеру, и каждая итерация занимает примерно
одинаковое время — тогда замер честно отражает O(log n).

## 3. Методика замеров

Как в `docs/reproducibility.md`:

- таймер `time.perf_counter()`;
- 8 запусков на точку, первый (прогрев) отбрасывается, по оставшимся 7 —
  медиана;
- размеры с геометрическим шагом: 10³…10⁵ для линейных и квадратичного
  алгоритма, 10³…10⁷ для показателя степени в `binary_pow`;
- фоновые приложения закрыты, ноутбук от сети.

Для трёх первых алгоритмов — график log-log (степенная зависимость на нём
превращается в прямую, наклон = показатель степени). Для `binary_pow` —
отдельный график t от log₂n в обычных линейных осях, а не log-log.

**Почему не log-log для binary_pow.** У меня n выросло в 10 000 раз (с 10³
до 10⁷), а время — всего в 2.2 раза. На log-log графике такая зависимость
почти не отличается от горизонтальной линии, наклон толком не разглядеть.
Логарифм от log(n) — это уже почти константа, поэтому лог-лог тут не
работает. А вот если по оси x откладывать сразу log₂n, а не n, то
зависимость t = c·log₂n становится обычной прямой линией — это и видно
на графике.

## 5. Сопоставление теории и практики

| Алгоритм | Теория | Наклон по графику | Совпадает? |
|---|---|---|---|
| array_sum | O(n) → 1 | 1.01 | да |
| array_max | O(n) → 1 | 1.03 | да |
| count_equal_pairs | O(n²) → 2 | 1.95 | да, с небольшим отклонением |
| binary_pow | O(log n) | график линеен по log₂n | да |

Наклоны получились очень близко к теории — расхождение в пределах пары
процентов, это обычный шум замеров, а не ошибка в алгоритмах. Основная
причина — на маленьких n (доли микросекунды) относительно заметнее
накладные расходы самого интерпретатора и вызова функции, они не растут
пропорционально n и немного искажают наклон именно на левом краю графика.
У `count_equal_pairs` наклон 1.95 вместо 2 — тоже в пределах этой же
погрешности: метод наименьших квадратов считается всего по 5 точкам,
так что небольшое отклонение ожидаемо.

### 6.1 Инварианты

| Функция | Инвариант |
|---|---|
| array_sum | сумма не зависит от порядка элементов (перемешал массив — результат тот же) |

- пустой массив, один элемент;
- все элементы равны (проверено для `array_sum`, `array_max`, `count_equal_pairs`);
- массив без повторов — отдельно для `count_equal_pairs` (результат должен быть 0);
- `binary_pow` — n=0, обычная степень без модуля, степень с модулем.

## 7. Ответы на вопросы для защиты

**1. Что такое асимптотическая сложность и чем различаются O, Θ и Ω?**

Асимптотика показывает, как время работы растёт с увеличением размера
входа n, без учёта констант и конкретного железа. O — верхняя граница
(«не медленнее f(n)»), Ω — нижняя («не быстрее f(n)»), Θ — точная оценка,
когда выполняются обе одновременно. Например, `count_equal_pairs` — это
Θ(n²), а не просто O(n²): двойной цикл всегда проходит все n(n-1)/2 пар
независимо от содержимого массива.

**2. Как определяются худший, средний и лучший случаи?**

Для входа размера n берут все возможные входы этого размера и смотрят на
число операций T. Худший случай — максимум T по всем входам, лучший —
минимум, средний — матожидание при каком-то распределении входов. У
`array_max` все три случая совпадают (O(n)): цикл всегда проходит все n
элементов, входные данные меняют только число обновлений `max_val`, но
не число итераций.

**3. Почему на log-log графике степенная зависимость — прямая?**

Если t = c·n^k, то после логарифмирования: log(t) = log(c) + k·log(n) —
это уравнение прямой, где k — угловой коэффициент. Поэтому наклон на
log-log графике и есть показатель степени: у меня 1.01 и 1.03 для линейных
алгоритмов, 1.95 для квадратичного — почти точно 1 и 2, как в теории.

**4. Какие искажения вносят интерпретатор, кэш и фон, и как методика их компенсирует?**

Интерпретатор Python добавляет константные накладные расходы на каждый
вызов — заметнее на малых n, где всё измерение занимает микросекунды.
Кэш процессора ускоряет доступ к маленьким массивам и создаёт излом на
графике, когда данные перестают помещаться в кэш. Фоновые процессы дают
случайные всплески времени. Методика компенсирует это прогревом (первый
запуск не считается), несколькими повторами с медианой вместо среднего
(выброс не сдвигает медиану) и закрытием фоновых приложений перед замером.
