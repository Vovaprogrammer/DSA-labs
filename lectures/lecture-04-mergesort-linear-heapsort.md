## 1. Сортировка слиянием

Сортировка слиянием делит массив на две половины по индексу середины, рекурсивно сортирует обе половины и сливает упорядоченные половины в одну упорядоченную последовательность. В QuickSort основная работа выполняется при разбиении, в MergeSort — при слиянии; деление пополам сравнений не требует. Алгоритм предложил Дж. фон Нейман в 1945 году.

```python
def merge_sort(a):
    if len(a) <= 1:
        return list(a)
    mid = len(a) // 2
    left = merge_sort(a[:mid])
    right = merge_sort(a[mid:])
    return merge(left, right)

def merge(left, right):
    out, i, j = [], 0, 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:       # при равенстве — левый
            out.append(left[i]); i += 1
        else:
            out.append(right[j]); j += 1
    out.extend(left[i:])              # остатки
    out.extend(right[j:])
    return out
```

На каждом шаге слияния сравниваются первые необработанные элементы списков, и меньший переносится в результат; когда один список исчерпан, остаток другого копируется без сравнений. Например, left = [2, 4, 5, 7] и right = [1, 2, 3, 6] сливаются за 7 сравнений: 2 > 1, 2 ≤ 2, 4 > 2, 4 > 3, 4 ≤ 6, 5 ≤ 6, 7 > 6, после чего остаток [7] дописывается без сравнений. Каждое сравнение переносит один элемент, а последний элемент переносится без сравнения, поэтому слияние списков суммарной длины m требует не более m − 1 сравнений и выполняется за Θ(m).

Массив 5, 2, 4, 7, 1, 3, 2, 6 сортируется так: восемь отрезков по одному элементу (они упорядочены), затем пары 2 5, 4 7, 1 3, 2 6, затем четвёрки 2 4 5 7 и 1 2 3 6, затем весь массив 1 2 2 3 4 5 6 7.

## 2. Трудоёмкость сортировки слиянием

На каждом уровне дерева рекурсии сливаются отрезки общей длиной n, поэтому уровень стоит не больше n сравнений, а уровней ⌈log₂ n⌉. Рекуррентность T(n) = 2T(n/2) + Θ(n) по второму случаю мастер-теоремы даёт T(n) = Θ(n log n).

### Разбор 1. Число сравнений MergeSort

Слияние списков длины p и q делает не больше p + q − 1 сравнений и не меньше min(p, q): минимум достигается, когда все элементы одного списка меньше элементов другого. Для n = 2ᵐ уровней m = log₂ n, и на каждом уровне n/2ᵏ слияний пар отрезков длины 2ᵏ⁻¹:

```
лучший случай:  (n/2)·log₂ n
худший случай:  n·log₂ n − n + 1           n = 8: 12 и 17
общая формула худшего случая:
W(n) = n·⌈log₂ n⌉ − 2^⌈log₂ n⌉ + 1
n = 1000: 1000·10 − 1024 + 1 = 8977
```

При n = 1000 MergeSort делает на случайном входе около 8 700 сравнений, на упорядоченном — 4 932, на обратном — 5 046, а в худшем случае — 8 977. На упорядоченном входе сравнений примерно вдвое меньше: левая половина исчерпывается первой, и правая копируется без сравнений.

Оценка Θ(n log n) выполняется для любого входа: деление идёт строго пополам по индексу, и вырожденного разбиения, как у QuickSort, не бывает. Обратная сторона — алгоритм не адаптивен: упорядоченность входа уменьшает лишь константу.

## 3. Стабильность и дополнительная память

Элементы левой половины во входе предшествуют элементам правой. Условие `left[i] <= right[j]` при равных ключах выбирает элемент левой половины, поэтому порядок равных элементов сохраняется на каждом уровне рекурсии, и MergeSort стабилен. Замена `<=` на `<` не нарушает упорядоченность результата, но делает сортировку нестабильной: при равных ключах первым уходит элемент правой половины.

Пример: левая половина 1a 2b 2c, правая 2d 3e (число — ключ, буква — метка исходного положения). С условием `<=` получается 1a 2b 2c 2d 3e — порядок b, c, d сохранён. С условием `<` получается 1a 2d 2b 2c 3e — d обогнала b и c. По ключам оба результата упорядочены, поэтому тест на числах эту ошибку не обнаруживает: стабильность проверяют на парах «ключ, номер».

Буфер слияния требует Θ(n) дополнительной памяти. Срезы `a[:mid]` копируют n элементов на уровень, что оценку Θ(n log n) не меняет. Алгоритмы слияния без буфера известны, но сложны и на практике медленнее. Глубина рекурсии равна ⌈log₂ n⌉: 20 уровней при n = 10⁶.

| Свойство | QuickSort (случайный опорный) | MergeSort |
| --- | --- | --- |
| Время | Θ(n log n) в среднем, Θ(n²) в худшем | Θ(n log n) в худшем |
| Память | стек O(log n), сортирует на месте | Θ(n) на буфер слияния |
| Стабильность | нет | да |

**Восходящее слияние** обходится без рекурсии: проходы сливают соседние отрезки длины width, а width удваивается на каждом проходе — 1, 2, 4, … Проходов ⌈log₂ n⌉, при n = 1000 их 10. Вариант удобен, когда рекурсия нежелательна или данные читаются последовательно.

**Естественное слияние** начинает не с отдельных элементов, а с максимальных упорядоченных участков входа — серий. На упорядоченном входе серия одна, и сравнения не нужны вовсе, тогда как обычный MergeSort при n = 10⁴ делает на том же входе 64 608 сравнений. На поиске серий основан Timsort — алгоритм `sorted()` и `list.sort()`.

## 4. Внешняя сортировка

Внешняя сортировка нужна, когда данные не помещаются в оперативную память. Она идёт в две фазы:

1. **Формирование серий:** файл читается блоками размера M (объём памяти), каждый блок сортируется в памяти и записывается на диск.
2. **Многопутевое слияние:** для каждой серии в памяти хранится буфер, а следующий элемент выбирается с помощью кучи из первых элементов серий (раздел 9).

### Разбор 2. Внешняя сортировка: расчёт

```
N = 100 ГБ, память M = 4 ГБ
серий: ⌈N / M⌉ = 25
фаза 1: прочитать 100 + записать 100
k = 25: один проход слияния: прочитать 100 + записать 100
        итого 400 ГБ ввода-вывода
k = 2:  ⌈log₂ 25⌉ = 5 проходов: 200 + 5·200 = 1200 ГБ
```

Число проходов слияния — ⌈log_k(N/M)⌉, и каждый проход читает и записывает весь объём N. Время внешней сортировки определяется числом проходов по диску, а не числом сравнений. При k = 25 на каждую серию приходится буфер 4 ГБ / 25 ≈ 160 МБ; извлечение минимума из кучи k серий и добавление следующего элемента той же серии стоят O(log k), всего O(N log k) сравнений за проход. Увеличение k сокращает число проходов, но уменьшает буферы и увеличивает число произвольных обращений к диску.

Внешнюю сортировку применяют СУБД (`ORDER BY` над большими таблицами; в плане запроса PostgreSQL она видна как «external merge»), утилита `sort` и системы MapReduce. В Python многопутевое слияние реализует `heapq.merge`.

## 5. Нижняя оценка для сортировок сравнением

Работу сортировки сравнением на входах размера n можно представить двоичным **деревом решений**: внутренний узел соответствует сравнению двух элементов, ветви — его исходам, лист — найденной перестановке. Каждой из n! перестановок входа соответствует свой лист, поэтому листьев не меньше n!. Число сравнений в худшем случае равно высоте дерева h, а двоичное дерево высоты h имеет не более 2ʰ листьев:

```
2ʰ ≥ n!  ⇒  h ≥ log₂ n!
```

Сортировка вставками трёх элементов — дерево с 6 листьями и высотой 3 = ⌈log₂ 6⌉.

### Разбор 3. log₂ n! = Θ(n log n)

```
Сверху: n! ≤ nⁿ  ⇒  log₂ n! ≤ n·log₂ n
Снизу:  последние n/2 множителей произведения n! не меньше n/2
        ⇒ n! ≥ (n/2)^(n/2)  ⇒  log₂ n! ≥ (n/2)·log₂(n/2)
Итог:   log₂ n! = Θ(n log n)
Стирлинг: n! ≈ √(2πn)·(n/e)ⁿ  ⇒  log₂ n! ≈ n·log₂ n − 1,44·n
```

**Теорема.** Любая сортировка сравнением делает в худшем случае не меньше ⌈log₂ n!⌉ = Θ(n log n) сравнений. Та же оценка справедлива для среднего числа сравнений.

| n | ⌈log₂ n!⌉ | MergeSort, W(n) |
| --- | --- | --- |
| 3 | 3 | 3 |
| 5 | 7 | 8 |
| 10 | 22 | 25 |
| 1 000 | 8 530 | 8 977 |
| 10⁶ | ≈ 18,5 млн | ≈ 19,0 млн |

В худшем случае MergeSort превышает нижнюю границу на 5 % при n = 1000 и на 2,5 % при n = 10⁶. Для n = 5 граница равна 7 и достигается алгоритмом Форда — Джонсона, а MergeSort в худшем случае делает 8 сравнений.

Следствия. MergeSort и HeapSort выполняются за Θ(n log n) в худшем случае, QuickSort со случайным опорным — в среднем, Timsort — за O(n log n) в худшем; все они асимптотически оптимальны, и дальнейшие улучшения касаются константы, памяти, стабильности и работы с кэшем, но не порядка роста. Нижняя оценка относится только к алгоритмам, которые получают информацию о данных через сравнения. Если ключи — целые числа ограниченного диапазона или строки фиксированной длины, значение ключа можно использовать как индекс массива. Так устроены сортировка подсчётом и поразрядная сортировка: элементы между собой не сравниваются, и теорема им не противоречит — они работают в другой модели вычислений.

## 6. Сортировка подсчётом

**Определение.** Сортировка подсчётом — сортировка целых ключей из диапазона [0, k − 1]: для каждого значения ключа считается, сколько раз оно встречается, и по этим счётчикам элементы сразу ставятся на свои места без сравнений.

```python
def counting_sort(a, k):
    count = [0] * k
    for x in a:
        count[x] += 1
    out = []
    for v in range(k):
        out.extend([v] * count[v])
    return out
```

Время Θ(n + k) — проход подсчёта и проход вывода; память Θ(k) на счётчики и Θ(n) на результат. Этот вариант восстанавливает значения по счётчикам и не подходит для записей с другими полями. Для записей используют устойчивый вариант с префиксными суммами:

```python
count = [0] * (key_max + 1)
for x in a:
    count[key(x)] += 1
for v in range(1, key_max + 1):
    count[v] += count[v - 1]
out = [None] * len(a)
for x in reversed(a):             # с конца
    count[key(x)] -= 1
    out[count[key(x)]] = x
```

После вычисления префиксных сумм count[v] равно числу элементов с ключом не больше v, то есть правой границе области ключа v в результате. Элементы входа просматриваются с конца и помещаются в последнюю свободную позицию своей области. Пример: вход 2a 0b 3c 2d 0e 1f (ключ и метка), счётчики ключей 0–3 — 2, 1, 2, 1, префиксы — 2, 3, 5, 6. Расстановка с конца: 1f — в позицию 2, 0e — в 1, 2d — в 4, 3c — в 5, 0b — в 0, 2a — в 3. Результат 0b 0e 1f 2a 2d 3c: пары 2a, 2d и 0b, 0e сохранили взаимный порядок — обход с конца обеспечивает устойчивость.

Оценка Θ(n + k) линейна только при k = O(n). Если диапазон ключей много больше числа элементов, время и память определяются массивом счётчиков: сортировка 1000 чисел занимает около 41 мс при k = 10⁶, 0,41 с при k = 10⁷ и 4,9 с при k = 10⁸ — время растёт пропорционально k при неизменном n. При ключах до 10⁹ массив счётчиков в Python занял бы около 7,5 ГиБ. Для диапазона [min, max] ключ сдвигают на min, тогда k = max − min + 1. Типичные применения — оценки по шкале 0–100, возраст, коды символов, дни недели.

## 7. Поразрядная сортировка

**Определение.** Поразрядная сортировка LSD — сортировка чисел устойчивыми проходами по отдельным разрядам, от младшего к старшему; после прохода по старшему разряду числа упорядочены.

Каждый проход — устойчивая сортировка подсчётом по одной цифре `(x // exp) % 10` с k = 10, а `exp` пробегает 1, 10, 100, … Числа 170, 45, 75, 90, 802, 24, 2, 66 сортируются за три прохода:

| Проход | По разряду | Результат |
| --- | --- | --- |
| вход | — | 170 045 075 090 802 024 002 066 |
| 1 | единицы | 170 090 802 002 024 045 075 066 |
| 2 | десятки | 802 002 024 045 066 170 075 090 |
| 3 | сотни | 002 024 045 066 075 090 170 802 |

Для наглядности числа дополнены ведущими нулями. Пустой вход обрабатывают отдельно: `max([])` вызывает исключение.

Инвариант LSD: после прохода по разряду j числа упорядочены по младшим j + 1 разрядам. Сохраняет его только устойчивый проход. Пример — 21, 12, 22, 11: после прохода по единицам получается 21 11 12 22. При сортировке по десяткам числа с равными десятками (11 и 12, 21 и 22) должны сохранить этот порядок; устойчивый проход даёт 11 12 21 22, а неустойчивый — например, расстановка с начала входа — 12 11 22 21, и результат первого прохода теряется.

Время — Θ(d·(n + b)), где d — число разрядов, b — основание (число значений одного разряда). Чем больше основание, тем меньше проходов: для ключей до 10⁹ основание 10 требует 10 проходов, основание 256 (байт) — 4, а для 32-битных ключей основание 2¹⁶ — 2. Проход по байтам к тому же дешевле десятичного: деление на степень десяти заменяется сдвигом и маской.

Линейные сортировки применимы к целым ключам небольшого диапазона и к ключам фиксированной длины (32- и 64-битные целые, IPv4-адреса, даты, строки одинаковой длины); на них сортируют большие массивы чисел на GPU и в СУБД. Они неприменимы или неэффективны, когда порядок задан функцией сравнения (строки переменной длины, записи с составным критерием), для вещественных и отрицательных чисел без преобразования ключа и при широком диапазоне ключей при малом n (k ≫ n). Линейные сортировки требуют дополнительных ресурсов — подсчёт Θ(k) памяти, поразрядная d проходов, — а реализация на Python может уступать встроенной `sorted()`, написанной на C, поэтому выбор подтверждают замерами.

## 8. Двоичная куча

**Определение.** Двоичная куча (max-heap) — почти полное двоичное дерево, в котором ключ каждого узла не меньше ключей его потомков; поэтому максимум всегда в корне.

Почти полное дерево заполнено по уровням слева направо и хранится в массиве без указателей:

```
parent(i) = (i - 1) // 2
left(i)   = 2 * i + 1
right(i)  = 2 * i + 2
```

Высота кучи из n элементов равна ⌊log₂ n⌋. Свойство кучи связывает только родителя и потомков; элементы одного уровня между собой не упорядочены, и массив-куча в общем случае не отсортирован. Например, [10, 5, 9, 4, 1, 8, 3] — max-куча: у корня 10 дети 5 и 9, у пятёрки — 4 и 1, у девятки — 8 и 3, но 9 стоит в массиве после 5.

```python
def sift_down(a, i, n):
    while True:
        big = i
        l, r = 2 * i + 1, 2 * i + 2
        if l < n and a[l] > a[big]:
            big = l
        if r < n and a[r] > a[big]:
            big = r
        if big == i:
            return
        a[i], a[big] = a[big], a[i]
        i = big
```

Просеивание вниз обменивает элемент с большим из потомков, пока свойство кучи нарушено; шагов O(log n). Кучу из произвольного массива строят просеиванием внутренних узлов от последнего к корню — листья уже являются кучами:

```python
for i in range(n // 2 - 1, -1, -1):
    sift_down(a, i, n)
```

Массив [4, 10, 3, 5, 1, 8, 9] после построения становится кучей [10, 5, 9, 4, 1, 8, 3].

### Разбор 4. Почему построение кучи стоит O(n)

```
высота h от низа | узлов     | спуск не больше
0 (листья)       | ≈ n/2     | 0
1                | ≈ n/4     | 1
2                | ≈ n/8     | 2
h                | ≈ n/2ʰ⁺¹  | h
Σ h·n/2ʰ⁺¹ = (n/2)·Σ h/2ʰ = (n/2)·2 = n
```

Ряд 1/2 + 2/4 + 3/8 + … сходится к 2, поэтому обменов при построении не больше n, а сравнений не больше 2n. Глубоко опускаются только узлы верхних уровней, а их мало; половина узлов — листья, и они не опускаются вовсе. При n = 10⁵ построение просеиванием делает около 188 тыс. сравнений — меньше 2n. Построение последовательными вставками с просеиванием вверх стоит O(n log n): глубоко поднимаются узлы нижних уровней, которых большинство, а на упорядоченном входе каждый новый элемент поднимается до корня — при n = 10⁵ это почти 1,5 млн сравнений.

## 9. Пирамидальная сортировка и `heapq`

```python
def heap_sort(a):
    n = len(a)
    for i in range(n // 2 - 1, -1, -1):
        sift_down(a, i, n)                 # куча
    for end in range(n - 1, 0, -1):
        a[0], a[end] = a[end], a[0]        # максимум — в конец
        sift_down(a, 0, end)
```

Корень (максимум) обменивается с последним элементом кучи и занимает окончательную позицию; размер кучи уменьшается на единицу, новый корень просеивается вниз; шаг повторяется n − 1 раз. HeapSort работает за Θ(n log n) в худшем случае (n − 1 просеиваний по O(log n)), сортирует на месте с O(1) дополнительной памяти и без рекурсии. Он **нестабилен**: обмен корня с последним элементом переносит элементы на большие расстояния — (2, a), (2, b), (1, c) превращается в (1, c), (2, b), (2, a). Сравнений HeapSort делает примерно вдвое больше, чем MergeSort (при n = 10⁵ — около 3,0 млн против 1,5 млн), а обращения по индексам 2i + 1 и 2i + 2 плохо используют кэш, поэтому на практике HeapSort медленнее.

Модуль `heapq` реализует min-кучу на списке: в корне находится минимум.

```python
import heapq
h = []
heapq.heappush(h, (3, 'отчёт'))
heapq.heappush(h, (1, 'авария'))
heapq.heappop(h)                  # (1, 'авария')
heapq.heapify(a)                  # O(n)
heapq.nlargest(10, a)             # 10 наибольших
heapq.merge(*runs)                # слияние упорядоченных серий
```

Применения кучи: очередь с приоритетом (вставка и извлечение минимума за O(log n) — планировщики задач, моделирование событий); выбор k наибольших элементов потока (куча размера k, время O(n log k), память O(k)); многопутевое слияние во внешней сортировке.

| Алгоритм | Лучший | Средний | Худший | Память | Стабилен |
| --- | --- | --- | --- | --- | --- |
| MergeSort | Θ(n log n) | Θ(n log n) | Θ(n log n) | Θ(n) | да |
| HeapSort | Θ(n log n) | Θ(n log n) | Θ(n log n) | O(1) | нет |
| QuickSort, случайный опорный | Θ(n log n) | Θ(n log n) | Θ(n²) | O(log n) | нет |
| Подсчётом | Θ(n + k) | Θ(n + k) | Θ(n + k) | Θ(n + k) | да |
| Поразрядная LSD | Θ(d(n + b)) | Θ(d(n + b)) | Θ(d(n + b)) | Θ(n + b) | да |
| Timsort (`sorted`) | Θ(n) | Θ(n log n) | Θ(n log n) | O(n) | да |

k — размер диапазона ключей, d — число разрядов, b — основание.

## Вопросы для самопроверки

1. Как изменится результат MergeSort, если в слиянии заменить `<=` на `<`?
2. Почему подсчёт непригоден для ключей до 10⁹ при n = 1000?
3. Сколько сравнений минимум нужно, чтобы отсортировать 5 элементов?

<details>
<summary>Ответы</summary>

1. Числа по-прежнему будут упорядочены, но сортировка станет нестабильной: при равных ключах строгое «меньше» ложно, и первым берётся элемент из правой половины, который обгоняет равный ему элемент левой. На обычных числах этого не видно — только на парах «ключ, метка».
2. Время и память — Θ(n + k), а здесь k в миллион раз больше n: нужен массив из миллиарда счётчиков (около 7,5 ГиБ в Python), и почти вся работа уходит на счётчики, а не на элементы. Для таких ключей берут поразрядную сортировку или сортировку сравнением.
3. Семь в худшем случае. Перестановок 5! = 120, а дерево решений высоты h имеет не больше 2ʰ листьев: 2⁶ = 64 < 120 ≤ 128 = 2⁷. Семи сравнений достаточно — это показывает алгоритм Форда — Джонсона; MergeSort в худшем случае делает 8.

</details>
